# 설계 — THE FROM BRAIN

구현 기준 문서다. 값이 다르면 코드가 맞다.

## 1. 옵시디언과 다른 점

| 옵시디언 | BRAIN |
|---|---|
| 볼트 = 폴더 | 프로젝트 1개 = JSON 1개 (`내보내기`) |
| 노트 = 마크다운 파일 | 노드 = 기준(`knowledge/nodes.js`) 또는 분석 결과(판단 · 통합 인사이트) |
| `[[위키링크]]` | 이슈 설명에 `[[노드 이름]]`을 쓰면 그 노드를 반드시 분석에 넣는다 |
| 백링크 | 노드 탭 — 낸 판단, 연결된 판단, 쓰인 인사이트 |
| 그래프 뷰 | 뇌 형상의 브레인 맵 |
| 링크에 종류가 없다 | 연결에 종류 · 무게 · 이유가 있다 |
| 사람이 직접 잇는다 | AI가 잇고 사람이 고친다 |

설치 · 플러그인 · 파일 시스템은 쓰지 않는다. 브라우저에서 연다.

## 2. 세팅 (`knowledge/tags.js`, `js/graph/model.js`)

사람마다 노드를 다르게 세팅하지 않도록 칸과 태그를 정해 두었다.

| 항목 | 내용 |
|---|---|
| 분류 6 | 마케팅 · 기획 · 디자인 · 개발 · 통합 · 서비스(자사) |
| 공통 인풋 6칸 | 무엇을 · 목적 · 타겟 · 제품·서비스 · 채널·매체 · 제약·메모 |
| 분류별 인풋 4칸 | 분류마다 4칸, 그중 2칸 필수 (예: 마케팅 = 목표 지표 · 오퍼/메시지) |
| 태그 41개 | 분류별 태그와 키워드. 이슈마다 1개 이상 |
| 이슈 | 제목 · 태그 · (근본 이슈면) 판정 질문 |

- **태그 추천** `recommendTags` — 이슈 글에서 키워드를 찾아 점수순으로 추천한다. 규칙 기반이라 같은 글이면 누가 넣어도 같은 태그가 나온다. 사람이 고르지 않으면 추천 3개를 자동으로 붙이고 "자동"으로 표시한다.
- **분류 추천** `recommendCategory` — 같은 방식으로 분류를 추천한다.
- **세팅 점검** `validateProject` — 빈 필수 칸과 분석에 못 들어가는 이슈를 문장으로 알려 준다. 필수 칸이 비면 분석을 시작하지 않는다.
- **개발 관점 필요 여부** `needsDevelopment` — 분류가 개발이거나 개발 태그가 붙은 이슈가 있으면 필요로 본다. 아니면 AI가 판단하고, 뺄 때는 이유를 쓴다.

### 브레인의 정의와 두 기준 (`knowledge/criteria.js`)

**어떤 인풋이라도 더프롬 방법론으로 브레인스토밍해, 차별화되면서 실효성 높은 결과를 낸다.** 결과는 이 두 기준으로만 판단한다.

| 기준 | 뜻 | 묻는 것 | 수준 |
|---|---|---|---|
| 차별화 | 다르다는 것만으로는 차별화가 아니다. 타겟에게 의미가 있고, 경쟁이 대신할 수 없고, 한 범주 안에서 기억되는 자리가 있어야 한다. 차이는 무엇과 견주느냐에서 생기고, 지금 이 사회에서 뜻하는 바가 있어야 한다 | 무엇과 견주어 다른가 · 타겟에게 왜 중요한가 · 왜 이 브랜드여야 하나 · 한 구절의 자리 · 따라오면 남는 것 · 지금 사회에서의 의미 | 다름에 그침 · 구분됨 · 차별화됨 · 자리를 가짐 |
| 실효성 | 조건을 통과하는지가 아니다. 실제 목적, 사회 현상, 타겟 행태, 비용, 구현 가능성, 그 밖에 걸리는 것을 모두 본 뒤 본래 목적을 얼마나 넘어설 수 있는지다 | 실제 목적 · 사회 현상 · 타겟 행태 · 비용 · 구현 가능성 · 그 밖의 이슈 · 목적을 넘어 얻는 것 | 목적 미달 · 목적 달성 · 목적 초과 (근거 있음 / 추정) |

### 판단 — 점수로 자르지 않는다

2차 평가에서 점수 합계가 무난한 안을 고르고 오차보다 작은 차이로 후보를 떨어뜨린 것을 확인했다(`docs/EVALUATION.md` §10). 그래서 다음과 같이 바꿨다.

- **점수가 없다.** 후보도 최종안도 숫자로 채점하지 않는다. 기준별 무게는 관점 글에서 무엇을 먼저 보는지를 정하는 데만 쓴다.
- **떨어뜨리는 것은 사유가 있을 때뿐이다.** 기본안과 같은 해법, 사람이 얻는 것이 없는 안. 제약을 넘는 것은 탈락 사유가 아니라 고칠 대상이다.
- **확인할 수 있는 것과 없는 것을 가른다.** 제약 · 접근성 · 팩트 근거 · 얻는 것 · N7은 통과 / 미달 / 확인 필요로 답한다. 차별화와 실효성은 물음에 답한 판정문과 수준으로 답한다. 글만으로 알 수 없는 것(새로 읽히는 느낌, 조형의 완성도)은 "보류"로 남기고 무엇을 보면 알 수 있는지 적는다. 답하지 못한 물음은 빈칸으로 두고 건수를 센다.
- **판정은 채택 · 보완 · 기각 · 보류.** 사람의 판정(판정 사례)이 엔진의 판정보다 위다. 경쟁에서 떨어진 "기본안과 다름" 후보는 따로 보여 주고 사람이 살릴 수 있다.

### 경쟁 — 종합 대신 겨루게 한다 (`js/engine/arena.js`)

분석을 하나로 종합하면 평균적인 안이 남는다. 그래서 묶음 통합안도 후보 중 하나로 두고 겨루게 한다. `settings.arena = false`면 묶음 통합안이 그대로 나온다.

| 단계 | 하는 일 | 호출 |
|---|---|---|
| 문제 다시 정의 | 기본안을 받은 뒤, 브리프와 다르게 묻는 문제 정의 3개를 만든다 | 1 |
| 노드의 완성안 | 노드가 판단과 함께, 자기 기준을 끝까지 민 완성안 1개를 낸다 | 0 (분석 호출에 포함) |
| 충돌 교배 | 충돌 연결이 강한 두 노드의 완성안으로 세 번째 안을 만든다. 5쌍 | 5 |
| 기본안 대조 | 후보를 기본안과, 그리고 후보끼리 견준다. 같은 해법끼리 묶음 이름을 붙인다. "같음"과 "얻는 것 없음"만 탈락 | 1 |
| 조별 대결 | 남은 후보가 3번씩 1:1로 겨룬다. 승수가 비슷한 후보끼리, 이미 만난 짝은 피한다 | 6 |
| 결선 자리 | 승수 상위 3 + 기본안과 다른 안 + 한 가지가 뚜렷한 안 + 상위를 이긴 안. 같은 해법은 2개까지 | 0 |
| 결선 | 6개가 모두 한 번씩 겨루고, 자리를 바꿔 한 번 더 판정한다. 두 판정이 갈리면 무승부로 두고 "판정 갈림"으로 표시한다 | 6 |
| 최종 3건 | 순위대로 뽑되 같은 해법 묶음에서는 하나만 | 0 |
| 공격 · 보완 | 이긴 3개의 약점을 찾아 고친다. 고친 뒤에도 컨셉 두 문장, 보이는 표현 네 문장 이내 | 6 |
| 재대결 | 고친 안과 고치기 전 안이 겨뤄 이긴 쪽을 남긴다 | 1 |

대진, 자리, 순위는 코드가 정한다. 대결 판정은 "약점이 없는 안"이 아니라 "더 멀리 가는 안"을 고르게 했다.

### 성공 기준과 범위 — 목적의 한 부분만 푼 안을 통과시키지 않는다

- 브리프에 "성공 기준" 칸이 있다(`knowledge/tags.js`). 무엇이 얼마나 달라지면 성공인지 한 줄.
- 근본 이슈 후보는 덮는 것(`covers`)과 못 덮는 것(`misses`)을 적는다. 못 덮는 것이 있으면 화면에 "목적 일부만 덮음"으로 표시한다.
- 문제 다시 정의 단계는 근본 이슈가 못 덮는 것(`gap`)을 적고, 성공 기준을 직접 겨눈 정의를 적어도 하나 낸다. 없으면 한 번 다시 받는다(`run.scope`).
- 기본안 대조는 후보마다 성공 기준에 닿는 정도(직접 · 간접 · 없음)를 적는다. 결선 상위에 "직접"이 없으면 닿는 안 하나에 자리를 준다.
- 판정 점검 항목에 "성공 기준"이 있다. 미달이면 실효성은 "목적 미달"이고 채택하지 않는다. 판정문이 달리 써도 `shapeVerdict`가 지킨다.

### 같은 해법 재확인 — 최종안은 서로 다른 해법이어야 한다

- 결선 뒤: 결선 6개와 예비 4개를 다시 견주어 같은 해법을 묶는다(`distinctPrompt`). 견주는 것은 사용자가 하게 되는 행동과 그 순간이다. 최종안은 묶음마다 순위가 가장 높은 하나. 자리가 비면 예비에서 다른 해법을 올리고, 그것도 없으면 줄여서 낸다.
- 보완: 순위대로 하나씩 고친다. 다른 최종안의 지금 모습을 함께 주고 그 장치를 가져다 쓰지 못하게 한다.
- 보완 뒤: 한 번 더 견준다. 고치다가 같아진 안은 고치기 전으로 되돌리고 기록에 남긴다.

### 기조 — 공격을 받아도 방향은 지킨다 (`js/engine/arena.js`)

받은 공격을 전부 고치게 하면 안이 무난해지고 서로 닮는다. 구분을 지키면서 고치려면 고치기 전에 지킬 것을 정해야 한다.

| 단계 | 하는 일 |
|---|---|
| 기조 세우기 | 이긴 안마다 거는 것(`bet`) · 핵심 장치(`device`) · 포기한 것(`givesUp`)을 정한다. 안끼리 겹치면 안 된다 |
| 공격 | 기조를 알고 공격한다. 기조를 버리라는 요구는 공격이 아니다 |
| 보완 | 순위대로 하나씩. 공격마다 고침 · 대가 · 받지 않음 가운데 하나로 답한다. "고침"은 이 안의 장치를 더 밀어서 한다. 다른 최종안의 기조와 장치는 가져다 쓰지 않는다 |
| 재대결 | 고친 안이 더 무난해져 뚜렷함이 줄었으면 고치기 전 안이 이긴다 |
| 기조 확인 | 고친 뒤 기조가 지킴 · 약해짐 · 버림 가운데 무엇인지, 다른 안과 같아지지 않았는지 본다. 버렸거나 같아졌으면 고치기 전으로 되돌린다 |

성공 기준은 기조보다 앞선다. "성공 기준" 공격은 대가나 받지 않음으로 답할 수 없다. 기조를 버렸거나 다른 안과 같아진 안은 이유를 붙여 한 번 다시 고치고, 그래도 같으면 고치기 전으로 되돌린다(5차 평가에서 나온 수정).

인사이트에는 기조, 감수한 대가(`costs`), 받지 않은 공격(`refused`)이 남는다. 화면에서는 약점 칸에 보인다. 숨기지 않는다 — 대가를 아는 안이 무난한 안보다 낫다.

### 오케스트레이션 — 어느 호출을 어느 모델에게 (`knowledge/orchestration.js`)

호출마다 급을 붙여 내보낸다. 공급자는 급에 따라 모델을 고른다(OpenAI: `models.lead` · `models.support`, Claude 페이지: 높은 단계 · 기본 단계).

| 급 | 호출 | 왜 |
|---|---|---|
| lead (주 모델) | 근본 이슈 · 기본안 · 문제 다시 정의 · 사조 훑기 · 판단 도출(아이덴티티 · 에어플레인) · 연결 · 충돌 교배 · 기조 · 보완 · 더프롬 판정 | 방향을 정한다. 틀리면 뒤가 전부 틀린다 |
| support (보조 모델) | 판단 도출(터널) · 묶음 정리 · 기본안 대조 · 대결 · 같은 해법 묶기 · 공격 · 기조 확인 · 디렉션 · 기획/디자인 틀 · 팩트북 조사 | 정해진 방향 안에서 정리하고 대조한다 |

근거는 `docs/EVALUATION.md` 12절이다. 결선 판정 30건은 두 모델이 27건 같았다(판정은 보조 모델로 충분). 보완은 같은 기조를 줘도 보조 모델이 다른 안의 구조를 가져왔다(주 모델에게 맡긴다). 기본안은 주 모델로 낸다 — 약한 모델로 내면 "기본안과 다름"이 방법론이 아니라 모델 차이에서 생긴다.

### Claude API (`js/providers/anthropic.js`, `api/claude.js`)

- 설정에서 "Claude API"를 고르면 주 모델(`claude-opus-5-5`)과 보조 모델(`claude-sonnet-5-5`)로 위 배정대로 부른다. 모델 이름은 설정에서 바꾼다.
- 키를 두는 곳은 둘이다. 내 키: 브라우저에서 직접 부른다(이 브라우저에만 저장). 서버 키: `ANTHROPIC_API_KEY`를 가진 `server.js`나 Vercel 함수 `/api/claude`가 대신 부른다. 사내 배포는 서버 키와 접속 코드를 쓴다.
- 조직 설정에 따라 브라우저 직접 호출이 막혀 있으면 서버 키로 쓴다.
- 호출 형식은 2026-11 문서를 따랐고 가짜 응답으로 테스트했다. 실제 키로는 아직 부르지 못했다.

### 화면 없이 돌리기 (`scripts/run-brain.mjs`, `docs/PROJECT-FILE.md`)

- `node scripts/run-brain.mjs 프로젝트.json --check` 는 파일만 검사한다. 키를 주면 같은 엔진으로 분석하고 결과(json)와 보고서(md)를 쓴다.
- 프로젝트 파일 규격은 `docs/PROJECT-FILE.md`다. 어느 LLM이든 RFP와 자료를 읽고 이 규격의 파일을 만들면 화면의 "프로젝트 가져오기"가 받는다. 스킬이나 MCP로 연결할 때 이 둘이 바탕이 된다.

### 사조 선정 — 사람이 고르지 않는다

사조 16개를 모두 과제에 한 번씩 대 보고(1회 호출), 걸리는 자리가 있는 것만 남긴다. 그중 압력이 뚜렷한 순으로 (필요한 수 − 1)개와, 걸리기는 했지만 가장 약한 것 1개를 일부러 넣는다(`selectByProbe`). 대립 쌍은 그 뒤에 맞춘다. 사람은 원할 때만 고정하거나 끈다.

### 프레임 — 이긴 안을 전통적인 틀로 정리한다 (`js/engine/frames.js`)

틀은 안을 만드는 단계가 아니라 정리하고 검증하는 칸이다. 경쟁 앞에 두면 표준 도구가 결론을 평균으로 당긴다. 그래서 경쟁과 판정 뒤에 둔다.

| 틀 | 칸 | 채우는 재료 | 호출 |
|---|---|---|---|
| 기획 | JTBD → 경쟁 구도 → 포지셔닝 → KSF → Key Claim → **Concept Theme** | 다시 정의한 문제, 터널 판단, 팩트, 기본안과 이긴 안의 차이, 받은 공격과 고친 것 | 1 |
| 디자인 | FoR → PoP → PoD(코어 · RTB) → **Creative 방향** | 기본안(PoP), 기본안에 없는 장치(PoD), 팩트(RTB), 사조의 읽기, 노하우북 | 2 |

- 칸마다 근거 id(N · R · B · F · 판단 id)가 있어야 한다. 근거가 없는 칸은 코드가 비우고 "채우지 못한 칸"으로 남긴다. 한 번 다시 쓴다.
- 기획 틀은 언제나, 디자인 틀은 분류가 디자인 · 통합 · 서비스이거나 디자인 태그가 붙은 이슈가 있을 때만 돈다.
- Concept Theme과 Creative 방향은 사람이 확정한다(화면의 확정 버튼).

### 노하우북 — 네 번째 재료 (`knowledge/knowhow.js`)

사조가 "왜 이렇게 하는가"라면 노하우북은 "무엇으로, 어떻게 만드는가"다. 스킬 저장소의 `catalog-form.md` PART B(Knowhow Book 3권)를 장 단위 16개, 항목 204개로 원문 그대로 가져온다(`npm run sync:knowledge`).

- **미리 고르지 않는다.** 이긴 안의 보이는 표현을 만들 때 생기는 조형 문제를 먼저 뽑고(1회 호출), 그 문제를 푸는 장만 최대 5개 부른다.
- **사조처럼 읽는다.** 장마다 푸는 문제 · 쓰는 조작(원문의 항목 id) · 무엇을 → 어떻게 · 빼면 달라지는 것을 쓴다. 무엇을 어떻게 바꾸는지 쓰지 못한 노하우는 코드가 뺀다. 부르지 않은 장의 노하우도 받지 않는다.
- 지금은 디자인 틀에서만 쓴다. 분석 단계의 노드군으로 넣는 것과 UI 패턴 카탈로그 · 질문 노드는 아직 옮기지 않았다.

### 더프롬의 관점 — 판단의 무게중심 (`knowledge/viewpoint.js`)

판단이 폭넓은 평균이 아니라 더프롬의 관점에서 출발하게 하는 장치다.

1. **모든 호출의 맨 앞에 관점을 넣는다.** "중립 심사자가 아니라 더프롬의 디렉터로 본다"는 지시, 기준 6개와 무게, 판정 사례가 들어간다. ⓪ 기본안만 예외다. 기본안은 더프롬의 관점 없이 낸 안이어야 비교 기준이 된다.
2. **기준별 무게.** 자메뷰 25 · 나로부터 20 · 사람이 얻는 것 20 · 1U 15 · 관성/해석 10 · 노랑 10 (%). 설정에서 바꾼다.
3. **판정 사례.** 대표와 디렉터가 실제로 내린 채택 · 기각과 이유다. 인사이트에서 채택 · 기각을 누르고 이유를 적으면 쌓인다. 프로젝트와 따로 저장하고, 최근 12건을 모든 분석에 넣는다. 처음 5건은 2026-11-25 대표 판정에서 옮겼다.
4. **아이덴티티 판단의 지지는 1.5배.** 묶기 계산에서 아이덴티티 판단과 연결된 판단의 지지도가 더 오른다 (`identityWeight`).
5. **더프롬 판정 (⑥′).** 점수를 매기지 않는다(위 "판단" 참고). 기각된 인사이트는 통합 디렉션의 근거로 쓰지 않는다.

### 사조 읽기 — 해도 되는 것 / 안 되는 것으로 나누지 않는다 (`knowledge/ism-depth.js`)

사조마다 시대 조건 · 던진 질문 · 사조 안의 갈래 · 내부 모순 · 후대의 변용을 적어 두었다 (16개, 초안 — 사내 검수 필요). 사조 노드는 이 자료와 카드 원문을 읽고 아래를 쓴다.

| 칸 | 내용 |
|---|---|
| `origin` | 어떤 시대 조건에서 무엇 때문에 나왔나 |
| `parallel` | 이 이슈에서 그때와 같은 압력 |
| `strand` | 고른 갈래와 이유, 다른 갈래였다면 달라질 점 |
| `paradox` | 사조의 모순이 이 이슈에서 나타나는 모습과 기울일 방향 |
| `reading` | 이 사조의 눈으로 읽은 해석 3~5문장 |
| `layer` · `degree` | 어느 층(태도 · 원리 · 방법 · 표현)에서 얼마나 세게(0~1) 쓰나 |
| `expression` | 표현 층일 때, 어떻게 보이는가 |
| `swap` | 이 사조를 빼면 무너지는 것 |

카드의 "가져올 것 · 두고 올 것"은 지난 적용 메모로만 보여 주고 규칙으로 쓰지 않는다. `treatment`(다섯 가지 중 택일)와 `leave` 칸은 없앴다.

### 팩트북 — 터널을 실제 자료로 좁힌다 (`knowledge/facts.js`)

| 항목 | 내용 |
|---|---|
| 종류 | 트렌드 · 타겟 습성 · 통계 · 공시 · 브랜드 공지 · 이슈 |
| 받는 출처 | 공식 통계 · 공시 · 브랜드 공식 자료 · 보도자료 원문. 직접 입력에 한해 내부 자료(브리프 · 클라이언트 자료) |
| 받지 않는 것 | 언론 기사 · 블로그 · 커뮤니티 · 위키 · 출처 없는 자료 |
| AI 조사 | 웹 검색이 되는 모델이 채운다(`researchFacts`). 원문 주소와 날짜가 없으면 코드가 버린다. 넣은 항목은 사람이 원문을 확인하기 전까지 "확인 전"으로 표시한다 |
| 파일 | md로 내보내고 다시 읽는다 (`factsToMarkdown` · `parseFactbook`) |

- 팩트북은 모든 노드에 전달한다. 터널 레이어는 자기 종류를 먼저 본다 (시장 = 트렌드 · 통계 · 공시 · 이슈, 브랜드 = 브랜드 공지 · 공시 · 이슈, 타겟 = 타겟 습성 · 통계, 사용 습관 = 타겟 습성 · 트렌드).
- 판단은 기댄 팩트의 ID를 적는다. 팩트북에 없는 ID는 코드가 지운다.
- **팩트 없이 쓴 터널 판단은 "추정"으로 표시하고 강도를 0.6배로 낮춘다.** 팩트북이 비면 터널 판단 전체가 추정이다.
- 인사이트마다 근거 팩트를 모아 보여 준다. 화면 요약에 "터널 판단 n건 중 팩트 근거 n건 · 추정 n건"을 표시한다.
- 2026-11-25 평가 실행에서는 터널 판단 10건의 출처가 추론 6건 · 브리프 4건이었고 실제 자료는 0건이었다.

### 깊이 — 노드를 훑지 않게 하는 장치

노드 이름과 정의만 읽고 쓴 판단은 결과를 바꾸지 못한다. 그래서 분석 단계에 세 가지를 넣었다.

1. **원문을 읽힌다.** 사조 노드는 카탈로그 카드 전문을, 아이덴티티 · 터널 노드는 CORE의 해당 절을 프롬프트에 그대로 넣는다 (`knowledge/isms.js`, `knowledge/core.js`).
2. **생각한 순서를 쓰게 한다.**

| 칸 | 내용 | 대상 |
|---|---|---|
| `origin` | 이 사조가 무엇에 반대해서 나왔나 | 사조 |
| `parallel` | 그 반대가 이 과제의 무엇과 같은 구조인가 | 사조 |
| `ladder` | 현상 → 왜 → 본질, 3단계 이상 | 전체 |
| `swap` | 다른 사조를 넣었다면 무엇이 달라지나 | 사조 |
| `against` | 이 판단에 대한 반론 | 아이덴티티 · 터널 |

3. **얕은 판단은 코드가 뺀다.** `ladder`가 3단계 미만이거나 사조 판단에 `origin` · `parallel` · `reading`(또는 `swap`)이 비어 있으면 제외하고 건수를 기록한다.

### 기본안 대조 — 브레인을 쓴 효과를 실행마다 확인

1. ⓪에서 받은 기본안 3개(B1~B3)를 ⑤ 통합 프롬프트에 넣는다. 인사이트는 가장 가까운 기본안(`without.nearest`)과 차이(`without.difference`)를 써야 한다.
2. ⑦에서 다른 호출이 인사이트마다 `같음` · `일부` · `다름`을 판정한다(`direction.overlap`). 인사이트를 쓴 호출이 스스로 판정하지 않게 나눴다.
3. 화면과 보고서에 건수로 표시한다. `같음`이 있으면 경고를 띄운다.

넣은 이유: 2026-11-25 평가에서 2.0 인사이트 3건 중 1건이 기본안과 같은 해법으로 판정됐다 (`docs/EVALUATION.md`).

### 분류 — 여러 개 고른다 (`knowledge/tags.js`)

분류는 일곱 가지다: 마케팅 · 기획 · 디자인 · 개발 · 통합 · 서비스(자사) · 운영. 한 프로젝트가 여러 분류를 고를 수 있고, 고른 분류마다 특화 인풋 4칸이 열려 미션에 함께 들어간다. 예전 프로젝트(`category` 하나)도 그대로 읽는다.

## 5. 계산 (`js/graph/propagate.js`)

**지지도**

```
e ← (1 − d)·강도 + d·(1 − exp(−지지))        d = 0.5, 24회 반복
지지 = Σ 무게 × 이웃의 지지도 × (다른 노드군 1 · 같은 노드군 0.5)
```

원인 · 조건은 결과 쪽으로 전부, 전제 쪽으로 절반 전달한다. 강화는 양쪽으로 전달한다. 충돌은 전달하지 않는다.

**묶음** — 판단 하나에서 시작해, 지금 묶음과 연결 무게 합이 가장 큰 판단을 1건씩 더한다. 같은 이슈면 1.25배, 합이 0.5 미만이면 멈춤, 최대 7건. 자리가 얼마 안 남았는데 빠진 노드군이 있으면 그 노드군부터 넣는다.

```
점수 = 지지도 합 × 노드군 범위(1군 0.2 · 2군 0.6 · 3군 1) × (1 + 0.2 × 묶음 안 충돌 수)
```

점수순으로 N개를 고르고, 이미 고른 묶음과 절반 이상 겹치면 건너뛴다. 충돌에 가산점을 주는 근거는 CORE §6.1이다.

## 6. 검증

**통합 인사이트 `checkInsight`**

| 걸리는 조건 | 뜻 |
|---|---|
| 거친 판단이 3건 미만 | 요약에 그쳤다 |
| 묶음에 있는 노드군 중 거치지 않은 것이 있다 | 한 단계만 인용했다 (1.x의 문제) |
| 근거 노드가 3개 미만 | 한 노드만 반영했다 |
| 묶음이 2개 노드군 미만이다 | 통합이 아니다 |
| 충돌이 있는데 해결 방법이 없다 | 충돌을 건너뛰었다 |
| 근본 이슈에 대입한 결과가 없다 | 이슈에 답하지 않았다 |
| `without`이 비었다 | 기본안과의 차이를 말하지 못했다 |

묶음에 없는 판단 ID는 빼고 `foreign`에 센다. 검증은 문장을 해석하지 않고 ID와 빈칸만 센다.

**통합 디렉션 `checkDirection`** — 관점마다 방향 · 바로 할 일 · 근거 인사이트 ID가 있어야 한다. 총괄 한 문장과 먼저 할 일 2건 이상이 있어야 한다. 개발 관점을 뺐으면 이유가 있어야 한다. 기본안이 있으면 모든 인사이트에 대조 판정이 있어야 한다. 어느 관점에도 쓰이지 않은 인사이트는 `unusedInsights`로 남긴다.

## 7. 공급자

```js
{ name, label, json({ role: 'director'|'brain'|'sub', system, user, signal, task }) → { json, usage? } }
```

`task`는 목업 전용이다. 새 공급자는 `js/providers/`에 같은 형태로 추가하고 `app.js`의 `getProvider`에 한 줄을 넣는다.

| 역할 | 쓰는 단계 |
|---|---|
| `sub` | ⓪ 기본안 · ② 분석 |
| `brain` | ① 사조 고르기 · ③ 연결 |
| `director` | 이슈 뽑기 · ⑤ 통합 · ⑥′ 더프롬 판정 · ⑦ 통합 디렉션 |

웹 조사는 `research({ system, user, signal })`를 가진 공급자만 한다. 지금은 OpenAI 공급자에만 있다(Responses API의 웹 검색 도구). 실제 키로는 확인하지 못했다.

## 8. 보안

## 입력 — 사람은 과제 정의만 쓰고, 나머지는 자료와 조사에서 채운다 (2026-11-26)

| 무엇 | 누가 채우나 | 어디 |
| --- | --- | --- |
| 목표 · 목적 · 성공 기준 · 핵심 포인트 · 제약 | 사람이 문장으로 | 미션 1 과제 정의 |
| 타겟 · 제품 · 채널 · 분류 · 영역 · 이슈 · 내부 자료 팩트 | 올린 자료에서 | 미션 2 자료 올리기 (`engine/intake.js`) |
| 시장 · 경쟁사 · 타겟 행동 · 이슈 팩트 | 딥리서치 에이전트가 웹에서 | 미션 5 팩트북 (`api/research.js`, `providers/research.js`) |
| 아이덴티티 · 터널 · 사조 | 기본으로 있다 | 미션 6 기본 노드 |

분류별 상세 인풋은 없앴다. 방향과 그 과정에서 나온 내용이 기획 · 디자인 프레임의 재료다. 예전 프로젝트에 적힌 값은 그대로 미션에 들어간다.

### 자료 올리기 (`js/engine/intake.js`)

- 여러 파일을 한 번에 올린다(최대 20개). PDF · 이미지는 그대로, Word · PowerPoint · Excel · HWPX는 브라우저 안에서 글로 풀어(ZIP을 직접 푼다 — 라이브러리 없음) 보낸다. HWP · 옛 오피스 형식은 읽지 못하고 이유를 보여 준다.
- ① 파일마다, 긴 글은 9만 자씩 나눠 **전부** 읽고 항목(과업 · 범위 · 요구 · 평가 · 일정 · 제약 · 현황 · 수치…)을 뽑는다 — 보조 모델. ② 뽑은 항목 전부를 놓고 배경 · 분류 · 영역 · 이슈 · 팩트로 정리한다 — 주 모델.
- 사람이 쓴 것은 덮어쓰지 않는다. 빈 칸만 채우고 이슈 · 팩트는 더한다. 과제 정의는 **초안**으로만 보여 주고 사람이 가져와 고쳐 쓴다.
- 자료에서 온 팩트는 출처가 파일 이름 · 쪽이고 "확인 전"이다. 원본은 저장하지 않는다 — 분석한 자료의 이름과 요약만 프로젝트에 남는다.
- 한도: 배포 서버는 요청 한 번에 4.5MB까지만 받는다. PDF · 이미지는 3MB까지다(글로 푸는 문서는 크기 제한에 걸리지 않는다).

### 딥리서치 에이전트 (`api/research.js`)

Claude 콘솔에서 만든 에이전트(Managed Agents)를 ID로 부른다. 에이전트의 지시문 · 모델 · 도구는 콘솔에서 고친다 — 브레인을 다시 배포하지 않는다.

- 환경 `BRAIN_AGENT_ENV`, 에이전트 `BRAIN_AGENT_IDS`(쉼표). 기본값은 코드에 있다. 여기 적힌 에이전트만 부를 수 있다. 화면에는 콘솔에서 지은 이름이 뜬다.
- 조사는 Anthropic 쪽 세션에서 돈다. 서버는 세션을 열고(`start`) 진행 상황을 읽을(`poll`) 뿐이라 함수 실행 시간 한도에 걸리지 않는다. 화면은 8초마다 읽고, 닫았다 다시 열어도 이어 받는다(`project.research`).
- 지시문에는 과제의 정의와 배경만 넣는다(`researchPrompt`). 자료 원문은 보내지 않는다.
- 답은 팩트북 마크다운으로 받는다. 출처 유형(공식 통계 · 공시 · 브랜드 공식 자료 · 보도자료) · 원문 주소 · 날짜가 없는 항목은 받지 않고, 받은 것은 "확인 전"으로 들어간다(`factsFromReport`).
- 확인하지 못한 것: 실제 키로 부른 적이 없다. 이벤트 목록의 쪽 넘김 이름은 문서에서 확인하지 못해 두 가지를 다 받게 했다.

## 코어 — 조각을 한꺼번에 수렴시킨다 (v6, 2026-11-26)

**왜 바꿨나.** v5까지는 노드마다 결론(방향 문장)을 하나씩 내고, 그 결론끼리 이은 뒤, AI가 후보를 쓰고 AI가 골랐다. 단계가 차례로 흘렀고 "동시에 놓고 맞물리는 것을 찾는" 계산은 없었다. 실제 실행에서 노드 14개가 모두 같은 이슈(혜택)를 말했다(14/14). 같은 노드에게 결론 대신 조각을 받았더니 과제 전체 조각 33개 중 한 영역의 낱말이 든 것은 6개였다.

**무엇이 도는가** — 병렬 제약 충족(정합 네트워크). 사람이 여러 가지를 한꺼번에 놓고 맞는 것끼리 서로 올리고 어긋나는 것끼리 누르다 하나의 그림으로 가라앉는 과정을 계산으로 옮긴 것이다.

| 단계 | 무엇을 하나 | AI |
| --- | --- | --- |
| 구성 | 노드마다 과제 전체를 읽고 **조각** 8개를 낸다 — 관찰 · 제약 · 해석 · 지렛대. 결론은 내지 않는다 (`courseLensPrompt`, `shapeAtoms`) | 노드 수만큼 |
| 관계 | 조각 사이의 지지 · 모순, 목표를 깨는 조각을 매긴다. **두 번 따로**(순서를 뒤집어) 매기고 합친다 — 둘 다 본 것은 온전히, 한쪽만 본 것은 절반, 엇갈린 것은 뺀다 (`courseRelPrompt`, `mergeRelations`) | 2회 |
| 수렴 | 네트워크를 짓고 한꺼번에 가라앉힌다 (`buildNet`, `settle`). 같은 입력이면 언제나 같은 결과다 | 없음 |
| 제안 | 서로를 살리는 해석끼리 묶는다 (`proposals`). **하나로 모으지 않는다** | 없음 |
| 표현 | 제안마다 방향 문장으로 옮긴다. 결론을 새로 정하지 않는다. 비즈니스 이슈 문장으로 한 번 더 정제한다 (`coursePrompt`) | 1회 |
| 시험 | 영역 · 고유 · 약속 · 브리프 시험으로 순서를 매긴다. 제안은 모두 남는다 (`courseJudgePrompt`) | 1회 |

**방법론은 프롬프트의 문구가 아니라 네트워크의 구조다** (`graph/cohere.js`의 `COHERE`):

- 팩트와 사람이 쓴 목표에 기댄 조각은 올라간다. 목표 · 목적 · 핵심 포인트는 자료에서 뽑지 않고 **사람이 문장으로 쓴다**(`goalsOf` — 브리프의 무엇을 · 목적 · 성공 기준 · 핵심 포인트 · 제약).
- 제약은 지켜야 한다(`constraint`). 구조에 관한 조각은 지킨다(`structure`) — 관성은 구조에서.
- 과제 전체를 무엇으로 볼 것인가(전체 범위의 해석)는 서로 겨루는 가설이다. 받치는 사이가 아니면 서로 누른다(`rivalry`) — 새로움은 해석에서.
- 더프롬의 기준(아이덴티티)과 이어진 지지는 더 무겁다(`identityWeight`).
- 목표나 약속을 깨는 조각은 눌린다(`breaks`) — 우리가 통제할 수 없는 구간의 결과를 전제로 한 조각이 여기서 꺼진다.

**제안을 묶는 법.** 해석 두 개의 가까움을 네트워크에 물어서 잰다 — 한 해석을 빼고 다시 수렴시켰을 때 다른 해석이 얼마나 내려가는가. 같이 꺼지면 한 편, 살아나면 맞수다. 직접 이어지지 않아도 근거의 사슬로 이어진 사이가 잡힌다. 직접 모순되는 해석은 한 묶음에 들지 않는다. 합쳐서 얻는 것이 없어질 때까지 묶는다(`grain`). 과제 전체를 읽은 해석이 살아 있는 묶음이 먼저이고, 한 영역만 읽은 묶음은 영역 전략의 재료로 뒤에 선다. 점수는 받치는 근거 − 살아남은 조각과의 부딪힘 − 약속을 깨는 조각이다.

**사람이 만지는 곳** (전략 한 장의 "조각" 판 · `project.pins`, `settings.cohere`, `settings.proposalCount`):

- 조각을 **고정**하거나 **제외**하면 그 자리에서 다시 수렴한다. AI를 부르지 않는다. 문장은 "문장 다시 쓰기"로 다시 받는다(호출 4회).
- 제안 수, 더프롬 기준의 무게, 해석끼리의 경쟁, 묶는 폭, 제약의 무게.
- 다른 제안을 기준안으로 삼으면 영역별 전략과 전술만 다시 쓴다(`take`, 호출 1회).

**실제 조각으로 확인한 것** (맥도날드 과제, 노드 14개 · 조각 112개 · 관계 192건[지지 163 · 모순 29, 두 번 매겨 일치 91건]):

- 수렴 149회, 살아남은 조각 98개, 눌린 조각 13개. 눌린 해석 5개는 쿠폰 · 고객 여정 · 리텐션 쪽이다 — 통제할 수 없는 구간을 전제로 해서 꺼졌다.
- 제안: ① 기준 단위 하나 · 생성 규칙(해석 6개 · 노드 5개 · 근거 7개) ② 혜택 표기 · 기한의 일치 = 신뢰(해석 2개 · 근거 6개) ③ 리포트 = 다음 건의 판단 근거(해석 5개 · 노드 4개). 보안 영역의 "장애 = 브랜드 신뢰"는 한 영역의 읽기로 뒤에 섰다.
- 더프롬 기준의 무게를 1로 내려도, 묶는 폭을 두 배로 해도 ①은 그대로다.
- 통념 억제(통념적 해석에 음의 값)는 결과를 바꾸지 못해 뺐다. 처음 쓴 연결 요소 묶기는 문턱에 따라 한 덩어리(18개)이거나 조각났다 — 빼 보는 방식으로 바꿨다.

**한계.** 관계를 매기는 일은 여전히 AI의 판단이다(두 번 매겨 일치한 것이 192건 중 91건). 조각의 질이 낮으면 수렴도 낮다. 수렴 뒤 다시 조각을 받는 되먹임은 아직 없다. 실제 모델로 끝까지 돌린 결과는 아직 없다.

## 방향 — 모든 과제가 같은 길을 간다

과제의 종류(캠페인 · 서비스 · 운영 · 제안)에 따라 길이 달라지지 않는다. 층위를 고르는 설정은 없앴다.

| 순서 | 무엇을 하나 | 누가 |
| --- | --- | --- |
| 1. 방향 | 모든 노드가 **과제 전체**를 읽고 조각을 낸다 → 조각 사이의 지지 · 모순을 매긴다 → **한꺼번에 수렴**시킨다 → 서로를 살리는 해석의 묶음마다 제안 하나 → 시험 | `head()` — 아이덴티티 · 사조 · 터널의 모든 노드, 수렴은 `graph/cohere.js` |
| 2. 전술 | 노드가 **이슈마다** 판단한다 → 연결 → 묶음 → 경쟁 → 더프롬 판정 | `think()`의 기존 단계 — 같은 노드가 서브 노드로 일한다 |
| 3. 내려 쓰기 | 방향 → 영역별 전략 → 전술. 전술마다 어느 노드의 판단에서 나왔는지 남긴다 | `descend()` |

지키는 것:

- **방향은 이슈 하나에 붙지 않는다.** 방향을 정하는 호출은 브리프의 무엇을 · 목적 · 성공 기준 · 대상 · 제약을 받고, 이슈는 "과제 안의 문제들 — 참고"로만 받는다(`missionBlock(…, { high: true })`). 판정에 브리프 시험이 있다 — 이슈 하나만 풀거나 성공 기준의 일부에만 닿으면 "일부"이고, 전체에 닿는 후보 뒤로 간다.
- **방향이 정해지면 뒤의 모든 호출이 같은 방향을 받는다.** 이슈 높이의 노드 판단, 연결, 통합, 경쟁, 판정, 디렉션, 기획 · 디자인 틀의 미션 글 맨 앞에 "과제의 방향 — 이미 정해졌다"가 붙는다(`project.heading`). 아래 단계는 방향을 다시 정하지 않고 그 방향을 서게 하는 판단과 안을 낸다.
- **전술은 노드의 판단에서 나온다.** 전술마다 `from`에 판단 id를 적고, 서로 다른 노드 6개 이상이 전술에 쓰여야 한다. 판과 보고서에 "← 나온 노드"와 "전술에 쓰인 노드 n/m개"가 보인다.
- **영역**은 과제가 맡는 일의 범위다. 미션 탭에 적거나, 비워 두면 브리프에서 뽑는다. 결과물이 하나인 과제는 영역 하나로 간다 — 같은 길이다.
- 방향을 정하지 못해도 분석은 이어 간다. 방향 없이 이슈만 본 결과가 남고, 메모에 이유가 적힌다.
- 이어서 하기(새 이슈만 · 다시 묶기)는 앞서 정한 방향을 그대로 쓴다. 이미 있는 분석 위에서 방향만 다시 정하려면 `strategizeOnly()`(`chart()` = `head()` + `descend()`)를 쓴다. 이때 이슈 높이의 판단과 인사이트는 예전 것 그대로다 — 새 방향 아래에서 다시 받으려면 처음부터 다시 분석한다.

### 문구로 막지 못한 것은 기계가 막는다

같은 길로 처음 돌린 실제 실행(2026-11-26, 호출 69회, 입력 213만 토큰)의 방향은 "혜택 한 건 기록 운영"이었다. 뼈대(기획자 판단이 붙은 기록이 쌓여 다음 해의 기준이 된다)는 처음으로 연간 운영 논리가 됐지만 단위가 또 한 영역(프로모션)의 대상이었다. 열어 보니:

- 과제 전체를 본 노드 판단 14건이 전부 혜택 이야기였고, 그중 8건은 거의 같은 문장이었다. 노드가 병렬로 다르게 보지 않았다. 미션의 판정 질문에 있던 표현("5개 파트와 1~12월")을 노드 5개 이상이 그대로 받아 썼다.
- 판정은 보안 영역의 결정으로 "혜택 기간에 따라 감시 등급을 올릴지"를 인정했다. 남의 영역의 대상을 빌린 줄이다.
- 프로모션 영역 전략의 이름이 "쿠폰 순서 혜택 칸 화면"이었다. 전술이 한 층 올라왔다.
- 이슈 높이의 판단이 50건에서 27건으로, 인사이트가 3건에서 2건으로 줄었다. 방향을 "따를 것"으로 주자 노드가 판단을 줄였다.

세 번의 실제 결과(혜택 값 → 혜택을 받아 쓰는 동선 → 혜택 한 건)가 모두 같은 자리에 붙었다. 프롬프트의 문구와 판정만으로는 못 막는다는 뜻이라, 낱말을 대조하는 검사를 넣었다.

| 막는 것 | 방법 |
| --- | --- |
| 방향이 한 영역의 대상에 붙는다 | 영역마다 **대상 낱말**(그 영역에서만 다루는 것, 3~6개)을 둔다. 사람이 미션에 적거나 비워 두면 뽑는다. 방향 문장에 한 영역의 낱말만 들어 있으면 표시하고 다시 쓰게 한다(`objectHits`). 두 영역 이상에 적힌 낱말은 걷는다 |
| 영역 줄 · 영역 전략이 남의 대상을 빌린다 | 제 영역의 낱말은 없고 다른 영역의 낱말만 있으면 표시하고 다시 쓰게 한다 |
| 영역 전략에 전술이 올라온다 | 영역 전략의 이름과 한 줄에 장치 이름(화면 · 칸 · 버튼 …)이 있으면 다시 쓰게 한다. 제 영역의 대상 낱말은 장치로 치지 않는다 |
| 노드가 같은 말을 한다 | 통합 판단끼리 두 글자 조각이 겹치는 비율을 잰다(`overlap`, 기준 0.3 — 실제 실행에서 거의 같은 문장은 0.3~0.5, 다른 문장은 0.2 아래였다). 앞선 노드와 겹치거나 한 영역의 대상에 붙은 노드는 다른 노드의 판단을 보여 주고 **한 번 다시 받는다**. 달라진 것만 바꾼다. 다시 받고도 남으면 "확인할 문제"에 적는다 |
| 노드가 과제의 문장을 받아 쓴다 | 노드는 "제 기준에서만 보이는 것"을 먼저 쓰고 거기서 판단을 낸다. 브리프 · 판정 질문 · 이슈의 문장을 되받아 쓰지 않게 한다 |
| 방향을 받은 노드가 판단을 줄인다 | 이슈 높이의 노드에게는 방향을 "따를 것"이 아니라 "시험할 것"으로 준다 — 방향이 그 이슈에서 서는 조건, 무너지는 지점, 놓친 것. 그 뒤 단계(통합 · 경쟁 · 판정 · 디렉션 · 틀)는 방향 아래의 일로 받는다 |

한 가지 더 — **말**. 결과물은 과제의 맥락에 맞는 말로 쓴다. 마케팅 · 비즈니스 · 운영 과제는 그 분야의 실무 용어(타겟, 고객 여정, 접점, 전환, 리텐션, KPI, SLA)로 쓰고, 이미 통하는 용어를 일상어로 풀어 바꾸지 않는다. "손님의 길"은 "타겟 여정"의 쉬운 말이 아니라 다른 말이다. 미션이 일상어로 적혀 있어도 결과물은 용어로 옮겨 쓴다.

넓이를 세는 방식도 고쳤다. 전술이 기댄 이슈 높이의 판단을 "쓴 판단"으로 센다(앞서는 방향과 영역 전략이 인용한 것만 세어 0/27로 보였다).

아래는 이 구조에 이르기까지의 기록이다.

## 운영 방향 — 전략 과제는 위에서 아래로 쓴다

과제에는 두 층위가 있다. 미션 탭의 "과제의 층위"에서 고르고, 고르지 않으면 분류로 정한다(통합 · 운영 분류는 전략).

| 층위 | 내는 것 | 전략 한 장을 만드는 순서 |
| --- | --- | --- |
| 컨셉 | 문제를 푸는 안 하나 (캠페인 · 화면 · 크리에이티브) | 이긴 인사이트를 재료로 올려 쓴다 (`strategy.js`) |
| 전략 | 통합 운영 방향과 그 아래 영역별 전략 · 전술 (운영 · 연간 플랜) | 방향을 먼저 겨뤄 정하고 아래로 내려 쓴다 (`course.js`) |

왜 나눴는가. 맥도날드 통합 운영 제안의 두 번째 실행(2026-11-26)에서 넓이는 고쳐졌다(쓰인 판단 35/50건, 노드 14/15개, 터널 7/8건).
그런데 맨 위에 선 것은 "혜택 끝 화면에 다음 날짜를 고정"이라는 장치 하나였고, 판정도 그 안을 기각했다(목적 미달). 넓이가 아니라 층위의 문제였다.

- 모든 단계의 산출물 틀이 "안"(제목 = 수단 + 효과, 컨셉, 보이는 표현, 핵심 장치)이다. 운영 방향이 들어갈 자리가 없다.
- 경쟁의 잣대가 "기본안과 다른 해법"이다. 방향 수준의 안은 기본안과 닮아 보여 떨어지고 특이한 장치가 남는다(후보 8건 중 3건이 "기본안과 같음").
- 전략 한 장이 이긴 인사이트에서 올라간다. 전술을 일반화한 문장이 맨 위에 선다.

### 방향인지 가르는 시험대는 업무 영역이다

첫 구현(v2)은 "모든 파트와 전 기간에 걸리는가"로 방향을 갈랐다. 맥도날드 과제에서 돌려 보니 후보 3개의 주어가 모두 "혜택"이었고(혜택 값 하나 / 반복 혜택 우선 / 누구나 읽는 혜택 정보) 판정은 셋 다 방향으로 통과시켰다.
혜택은 다섯 파트가 모두 만지는 대상이라 파트 시험을 통과한다. 그런데 과제의 업무 범위로 보면 프로모션 한 영역에만 걸린다. 재료도 기울어 있었다 — 판단 50건 중 36건(72%)이 혜택 · 프로모션 이야기였다.

그래서 층을 업무 영역으로 가른다(대표 정리, 2026-11-26).

| 층 | 내용 | 맥도날드 과제의 예 |
| --- | --- | --- |
| 업무 영역 | 과제가 맡는 일의 범위. 직무나 시기가 아니다 | 앱 웹뷰 프로모션(UI/UX 포함 기획 · 디자인) / 유지보수 운영 / 보안 · 모니터링 |
| 1. 통합 운영 방향 | 영역 전부를 하나로 운영하는 기준 | — |
| 2. 영역별 전략 | 방향이 영역마다 되는 방침 | 프로모션 관리 전략 |
| 3. 전술 | 영역 전략 아래의 여러 할 일. 단계별로 놓는다 | "혜택 다섯 칸"은 프로모션 관리 전략 아래 전술 하나 |

- 업무 영역은 미션 탭에 사람이 적는다(`project.areas`). 비워 두면 미션에서 뽑아 쓰고 미션 탭에 옮겨 둔다.
- 한 영역의 대상을 주어로 삼은 문장은 아무리 넓게 써도 그 영역의 전략이다. 파트와 기간에 걸친다는 것만으로는 방향이 아니다.
- 판단의 수가 방향을 정하지 않는다. 판단이 몰린 영역의 대상을 방향의 주어로 삼지 않게 하고, 판단이 적은 영역은 미션과 팩트북에서 읽게 한다. 판단이 2건보다 적은 영역은 "판단 근거 얇음"으로 보인다.

### 방향은 방향 높이의 뉴럴링크에서 나온다

업무 영역을 시험대로 세운 뒤(v3) 다시 돌려 보니 방향은 "손님 동선 기준 운영"이었다. 영역 시험은 통과했지만 세 가지가 남았다.

- 방향이 인용한 판단 8건은 터널 4건과 아이덴티티 4건이었고 사조는 0건이었다. 핵심 문장은 터널(시장 · 사용 습관) 판단 두 건과 거의 같았다. 충돌을 푼 것이 아니라 강한 판단을 올려 쓴 것이다.
- 가장 더프롬다운 두 노드(자메뷰, 관성은 구조 · 새로움은 해석)는 방향에 없고 전술에만 있었다. "고객 여정 기준"은 경쟁사도 쓸 수 있는 문장이다.
- 판정은 두 번 연속 후보 3개를 모두 통과시켰다.

원인은 노드 분석이 이슈(전술 높이)에서 한 번만 돈다는 데 있다. "영역 전부를 어떻게 하나로 운영하는가"를 본 노드 판단은 그래프에 한 건도 없었고, 방향 단계는 이슈 높이의 판단을 재료로 읽는 단일 합성이었다. 그래서 방향 높이에서 뉴럴링크를 한 번 더 돈다(v4).

| 높이 | 누가 판단하는가 | 어디에 쓰이는가 |
| --- | --- | --- |
| 방향 | 모든 노드가 통합 판단 1개씩 (`run.course.signals`, scope ALL) → 서로 이어 충돌을 찾는다 | 통합 운영 방향 — 충돌을 푸는 자리에서 쓴다 |
| 영역 | 모든 노드가 영역마다 판단 1개씩 (scope S1…) | 영역별 전략 |
| 이슈 | 처음의 노드 분석 (`run.signals`) | 전술, 그리고 경쟁을 거친 인사이트 |

전략 과제의 순서(`chart()`):

0. **업무 영역** — 사람이 적었으면 그대로, 없으면 미션에서 뽑는다(호출 1회).
1. **방향 높이의 노드 판단** — 노드마다 자기 기준 하나로만 본다. 이슈에서 낸 판단은 배경으로만 받고 넓게 고쳐 써서 올리지 않는다. 다른 노드 이름으로 바꿔도 성립하는 판단은 버리게 한다. 호출은 노드 수만큼(아이덴티티 · 사조는 주 모델, 터널은 보조 모델).
2. **연결** — 통합 판단끼리 충돌과 강화를 찾는다. 표현이나 강조점만 다른 것은 충돌이 아니다.
3. **기본 방향** — 노드 없이 미션만 읽고 낸 운영 방향.
4. **방향 후보 3개** — 후보마다 충돌 하나를 맡아 두 쪽을 다 살리는 기준을 세운다(`courseSpines`: 아이덴티티가 낀 충돌이 먼저). 아이덴티티 판단 2개 이상이 뼈대이고 터널 판단이 받친다. 영역마다 달라지는 것, 충돌을 푸는 방법, 경쟁사가 그대로 쓸 수 없는 이유를 쓴다. 이슈 높이의 판단은 주지 않는다 — 판단이 몰린 영역(혜택 36/50건)으로 끌려가지 않게.
5. **방향 판정** — 통과가 기본값이 아니다. 영역 시험(영역마다 이 기준이 가르는 실제 결정 하나. 다른 영역의 대상을 빌린 결정은 세지 않는다), 고유 시험(경쟁사가 그대로 쓸 수 있으면 범용), 약속 시험(통제할 수 없는 구간을 기준으로 삼았는가). 방향이고 고유하고 약속할 수 있는 후보가 먼저다. 이긴 방향이 범용 · 영역 전략 · 통제 불가이거나 기본 방향이 더 낫다고 나오면 "확인할 문제"로 남긴다.
6. **아래로 내린다** — 영역 전략은 영역 높이의 판단에서 출발하고 방향 문장을 옮겨 붙이지 않는다. 미션의 성공 기준 · 평가 항목을 받지 못하면 "확인할 것"에 적는다. 전술은 이슈 높이의 판단이 재료다(영역마다 4개 이상, 단계마다 1개 이상, 맡는 파트 표시). 이긴 인사이트는 전술 하나로 놓인다. 통제할 수 없는 구간의 일은 "건의한다"로 쓴다.

통합 분류는 파트가 아니다. 방향이 곧 통합이다. 파트(운영 · 기획 · 개발 · 마케팅 · 디자인)는 전술을 맡는 사람으로 붙는다.

이슈 높이의 분석은 다시 돌리지 않는다. `strategizeOnly()`가 처음에는 노드 수 + 6회 안팎, 방향 높이의 판단이 이미 있고 영역이 그대로면 4~6회로 만든다(`fresh: true`면 노드 판단부터 다시 받는다). 결과는 `run.strategy`(v: 4)에 담긴다. 판에는 방향을 만든 노드, 푼 충돌, 방향 높이의 노드 판단 전체가 보이고, 누르면 브레인 맵에서 그 판단을 낸 기준 노드가 켜진다. v2 · v3로 만든 결과도 그대로 그려지고 다시 만들라는 안내가 붙는다.

남은 한계:
- 방향 높이의 판단은 브레인 맵에 따로 노드로 그려지지 않는다. 그 판단을 낸 기준 노드가 켜질 뿐이다.
- 방향 판정은 한 번이다. 대결처럼 두 번 판정해 갈림을 잡지 않는다.
- 전략 과제에서도 이슈 높이의 경쟁(후보 → 대결 → 공격 → 보완)은 "안" 단위로 돈다. 거기서 나온 인사이트는 전술로 쓰이므로 틀리지는 않지만, 전체 분석 호출의 절반 이상이 여기에 든다.

## 전략 한 장 — 인사이트를 뽑은 뒤의 단계

경쟁은 안을 날카롭게 만들지만 좁힌다. 이긴 인사이트는 판단 몇 개에서 나온 장치 하나다.
맥도날드 통합 운영 제안 실행(2026-11-25)에서 판단 52건 중 인사이트에 쓰인 것은 11건(21%)이었다. 아이덴티티 10/27, 에어플레인 1/14, 터널 0/11. 팩트는 판단 단계에서 50건 중 38건이 인용됐지만 인사이트 3건이 적은 팩트는 25건이었다.

그래서 인사이트 위에 층을 하나 둔다(`js/engine/strategy.js`, 프롬프트는 `knowledge/prompts.js`의 `strategyPrompt`).

- 주 모델이 미션, 이긴 인사이트, **전체 판단(쓰였는지 표시)**, 팩트북을 다시 받아 과제를 관통하는 전략 하나로 올린다. 인사이트는 전략 아래의 실행 장치로 자리를 잡는다.
- 출력은 컨셉(이름·한 줄), 원칙, 축(분류를 여러 개 골랐으면 파트마다 하나), 흐름(시간 순서), 푸는 것, 키우는 것, 확인할 것, 인사이트의 짧은 이름이다.
- 글자 수를 묶는다(`STRATEGY_CAPS`: 이름 14자, 한 줄 38자, 축 안내 44자, 할 일 28자). 읽는 문서가 아니라 보는 판이다.
- 조건: 축마다 팩트 2건 이상, 서로 다른 팩트를 전체의 30%(최대 15건) 이상, 인사이트에 쓰이지 않은 판단 6건 이상. 못 채우면 무엇이 모자란지 붙여 한 번 더 쓰게 한다.
- 넓이를 숫자로 남긴다(`strategy.coverage`): 팩트·판단·노드를 몇 건 썼는지, 인사이트만 볼 때는 몇 건이었는지.
- 이미 있는 분석 결과 위에 이 단계만 다시 돌릴 수 있다(`strategizeOnly`, 호출 1~2회).

화면에서는 우측 패널 왼쪽에 판으로 펼친다. 축을 누르면 브레인 맵에 그 축이 기댄 팩트·판단·기준 노드만 켜지고 고리가 둘린다.
보고서는 한 장(.html, A4 가로)으로 받는다. 전체 기록(.md)은 따로 남는다.

실제 모델로는 아직 돌리지 않았다. 목업과 테스트로만 확인했다.

## 그래프 통합안 — 후보를 한 노드의 시각에서 그래프 전체로 (2026-11-26)

노드로 나누는 이유는 배경 이슈를 전부 세워 놓고 한꺼번에 입체적으로 읽기 위해서다. 그런데 경쟁 단계가 그것을 다시 쪼개고 있었다.
맥도날드 통합 운영 제안 실행(2026-11-25)의 기록:

| 구간 | 수치 |
| --- | --- |
| 노드별 판단 | 52건, 전부 팩트 인용 |
| 연결 | 109건, 전부 서로 다른 노드 사이 |
| 묶기 | 묶음 3개 × 7건 = 21건만 통합 대상. 31건은 여기서 빠짐 |
| 후보 | 22건 중 노드 하나가 혼자 쓴 완성안 14건, 노드 2개 교배안 5건, 묶음 통합안 3건 |
| 대결 | 묶음 통합안 3건 전부 탈락. 이긴 3건의 출처는 판단 2건 · 4건 · 5건 |
| 공격 · 보완 | 3건 모두 "성공 기준" 심각도 3. 고친 안 3건 모두 재대결에서 탈락("무거워졌다"). 반영 0건 |
| 판정 | 보완 1건, 기각 2건(목적 미달) |

고친 것(`js/engine/arena.js`):

1. **후보는 그래프 통합안이다.** 무거운 충돌을 뼈대로 고르고(`weaveSpines`, 서로 다른 노드 짝 · 이슈가 몰리지 않게), 주 모델이 **모든 노드의 판단**을 받아 그 충돌을 푸는 원리 하나로 안을 쓴다(`weavePrompt`). 노드 5개 이상, 노드군 2개 이상, 터널 판단 포함, 팩트 5건 이상을 요구한다. 노드의 완성안은 후보에서 빠지고 재료로 들어간다. 교배(노드 2개)는 하지 않는다.
2. **대결 판정자가 근거의 넓이를 본다.** 후보마다 "노드 n개 · 판단 n건 · 팩트 n건"을 붙이고, "뚜렷함은 좁다는 뜻이 아니다"를 규칙에 넣었다. 덮어야 할 범위를 한쪽만 덮으면 덮은 쪽이 이긴다.
3. **재대결을 하지 않는다.** 고친 안을 그대로 받고, 기조를 버렸는지 · 다른 안과 같아졌는지만 확인한다(기존 기조 확인).
4. **보완은 그래프에서 근거를 끌어온다.** 그 안이 아직 쓰지 않은 판단 24건을 같이 주고, 끌어온 판단(`pulled`)은 그 안의 근거에 더한다.

`settings.weave = false`, `settings.rematch = true`로 예전 방식을 돌릴 수 있다(비교용).
묶음 크기(7건)는 그대로 뒀다. 키우면 입력 순서에 따라 묶음이 달라져 결정성이 깨졌다.
