# 더프롬 브레인 프로젝트 파일 만들기

첨부된 RFP · 팩트 자료를 읽고, 더프롬 브레인이 그대로 받는 프로젝트 파일(JSON) 하나를 만든다.
사용자는 이 파일을 브레인 사이트(https://thefrombrain.vercel.app)의 **미션 탭 → 프로젝트 가져오기**로 올린다. 올린 뒤 화면에서 직접 고칠 수 있다.

## 순서

1. 첨부 파일을 전부 읽는다. 파일이 없으면 RFP나 자료를 달라고 한다. 다 읽지 못한 파일이 있으면 답에 적는다.
2. 자료에 **적힌 것만** 옮긴다. 적히지 않은 칸은 빈 문자열로 둔다. 지어내지 않는다.
3. 분류를 고른다. 걸치면 여러 개 고른다(예: 운영 + 개발).
4. 고른 분류마다 특화 인풋 4칸을 채운다.
5. 팩트는 출처가 있는 것만 넣는다. 한 프로젝트에 40건 안팎까지. 미션과 닿는 것부터 고른다.
6. 이슈는 사용자가 미션을 직접 말했거나 자료가 문제를 분명히 적었을 때만 넣는다. 근본 이슈 1개, 하위 이슈는 4개를 넘기지 않는다. 이슈가 많을수록 실행이 길어진다. 말한 것이 없으면 비워 둔다(브레인이 후보를 낸다).
7. `프로젝트이름.json` 파일로 저장해 사용자에게 준다.
8. 답에는 네 가지만 적는다: 고른 분류, 비워 둔 필수 칸, 자료끼리 어긋나는 내용, 다 읽지 못한 자료.

## 형식

```json
{
  "title": "프로젝트 이름",
  "categories": ["ops", "dev"],
  "brief": {
    "what": "만들거나 풀 것 한 문장",
    "purpose": "끝나면 무엇이 되어야 하나",
    "success": "무엇이 얼마나 달라지면 성공인가",
    "points": "놓치면 안 되는 것 — 한 줄에 하나씩, 문장으로",
    "target": "누가, 어떤 순간에",
    "product": "대상이 되는 제품 · 서비스",
    "channel": "어디서 만나나",
    "note": "반드시 지킬 것, 쓰면 안 되는 것, 모르는 것, 비교 대상"
  },
  "seed": {
    "ops": { "cycle": "", "standard": "", "team": "", "review": "" },
    "dev": { "stack": "", "integrate": "", "nonfunc": "", "ops": "" }
  },
  "areas": [
    { "name": "영역 이름", "note": "이 영역에 드는 일", "objects": ["이 영역만의 대상 낱말"] }
  ],
  "facts": [
    { "id": "F1", "kind": "stat", "text": "사실 한 문장", "sourceType": "internal", "source": "문서 이름 12쪽 (원출처가 적혀 있으면 함께)", "date": "2026-10", "url": "", "by": "doc", "checked": false }
  ],
  "issues": [],
  "settings": { "look": { "kind": "brain" } }
}
```

## 칸의 뜻

**brief** — `what` · `purpose` · `target`은 필수다. 자료에 성공 기준(목표 수치, 평가 항목)이 있으면 `success`에 반드시 옮긴다. 수치가 없어 평가 기준에서 옮겼으면 그렇게 적는다. 공개되지 않은 것, 확인이 필요한 것, 초안끼리 어긋나는 곳은 `note`에 적는다. `points`(핵심 포인트)는 사람이 직접 쓰는 칸이다 — 자료에서 지어내 채우지 않는다. 사람이 말해 준 것이 있으면 그 문장 그대로 한 줄에 하나씩 옮긴다. 브레인은 `what` · `purpose` · `success` · `points` · `note`를 고정된 목표로 놓고 노드의 조각이 거기에 닿는지를 본다.

**areas** — 과제가 맡는 일의 범위를 1~4개로 나눈 것이다. 자료(RFP · 브리프)의 과업 · 결과물 범위를 그대로 따른다. 직무(기획 · 디자인 · 개발)나 시기로 나누지 않는다. UI/UX는 영역이 아니라 영역 안의 일이다. 이슈를 그대로 옮기지 않는다. 결과물이 하나인 과제는 하나만 적는다. 브레인은 방향이 이 영역 전부에 걸리는지로 방향과 영역 전략을 가른다. 자료에 범위가 없으면 빈 배열로 둔다. `objects`는 그 영역에서만 다루는 대상을 가리키는 낱말 3~6개다(예: 프로모션 영역이면 혜택 · 쿠폰 · 캠페인 · 응모). 다른 영역에서도 쓰는 말, 과제 전체에 쓰이는 말은 넣지 않는다. 브레인은 방향 문장에 한 영역의 낱말만 들어 있으면 다시 쓰게 한다.

**말** — 브리프 · 이슈 · 팩트는 그 분야에서 통하는 용어로 적는다(타겟, 고객 여정, 접점, 전환, 리텐션, KPI, SLA). 용어를 일상어로 풀어 쓰지 않는다. "손님의 길"이 아니라 "고객 여정"이다. 브레인의 모든 노드가 미션의 말을 따라 쓴다.

**categories와 seed** — 분류마다 4칸. 고른 분류의 칸만 넣는다.

| 분류 | 값 | 특화 인풋 (★ 필수) |
|---|---|---|
| 마케팅 | `marketing` | `kpi` 목표 지표★ · `offer` 오퍼·메시지★ · `media` 매체·기간·예산 · `rival` 경쟁 상황 |
| 기획 | `planning` | `problem` 문제 정의★ · `scope` 범위★ · `decider` 결정하는 사람 · `success` 성공 기준 |
| 디자인 | `design` | `deliverable` 결과물과 범위★ · `moment` 핵심 순간★ · `brand` 브랜드 자산·금지 · `spec` 디바이스·규격 |
| 개발 | `dev` | `stack` 플랫폼·스택★ · `integrate` 연동·데이터★ · `nonfunc` 성능·보안·접근성 · `ops` 일정·운영 주체 |
| 통합 | `integrated` | `parts` 파트와 역할★ · `milestone` 일정·마일스톤★ · `touch` 접점 목록 · `govern` 의사결정 구조 |
| 운영 | `ops` | `cycle` 운영 주기·범위★ · `standard` 응대·품질 기준★ · `team` 운영 인력·도구 · `review` 보고·개선 주기 |
| 서비스(자사) | `service` | `status` 지금 상태★ · `segment` 사용자 구분★ · `model` 수익 모델 · `resource` 운영 리소스 |

**facts**

- `kind`: `trend` 트렌드 · `habit` 타겟 습성 · `stat` 통계 · `disclosure` 공시 · `notice` 브랜드 공지(RFP 조건도 여기) · `issue` 사건·논란·규제
- 첨부 자료에서 옮긴 사실: `sourceType`은 `"internal"`, `by`는 `"doc"`, `checked`는 `false`. `source`에 문서 이름과 쪽(조항)을 적고, 자료에 원출처가 있으면 괄호로 함께 적는다.
- 웹에서 직접 조사한 사실: `sourceType`은 `stat` 공식 통계 · `disclosure` 공시 · `official` 브랜드 공식 자료 · `press` 보도자료 원문 중 하나, `by`는 `"ai"`, `url`과 `date` 필수. `"ai"`에 `"internal"`을 쓰면 브레인이 받지 않는다.
- 한 줄에 사실 하나. 수치는 원문 그대로 옮기고 단위와 기준 시점을 같이 적는다. 비율에는 건수를 같이 적는다.
- 자료가 "판독값", "추정", "보도 인용"이라고 밝힌 것은 `source`에 그대로 적는다.

**넣지 않는 것** — 예시·더미 데이터, 가정 위의 시뮬레이션 결과, 양식 설명용 수치.

**issues** — `{ "id": "I1", "root": true, "title": "누구의 무엇이 바뀌는가", "detail": "", "test": "판정 질문", "tags": [] }`. 근본 이슈는 `root: true`와 `test`를 채운다. `tags`는 비워 두면 브레인이 붙인다.

**settings.look** — 브레인 맵 모양. 기본은 `{ "kind": "brain" }`. 사용자가 모양을 말했을 때만 바꾼다: `burger` 햄버거 · `bulb` 전구 · `bolt` 번개 · `phone` 폰을 쥔 손 · `server` 클라우드와 서버.

## 하지 않는 것

- 자료에 없는 수치 · 사례 · 타겟 묘사를 채우지 않는다.
- 블로그, 커뮤니티, 출처 없는 기사, 기억에서 나온 수치는 팩트로 넣지 않는다.
- 해법을 이슈 문장에 넣지 않는다. 이슈는 "누구의 무엇이 바뀌는가"다.
- 인사이트나 방향을 미리 쓰지 않는다. 그것은 브레인이 한다.
- RFP의 담당자 이름 · 전화번호 · 메일 같은 개인 연락처는 옮기지 않는다.
